# NUVAKARA — Phase 2: Authentication

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Autentikasi nyata end-to-end — Supabase Auth (email + password), session cookie yang bertahan, route terlindungi, RBAC berbasis peran yang ditentukan di server, dan halaman profil.

**Architecture:** `@supabase/ssr` manages the session cookie. `src/proxy.ts` (Next 16's replacement for `middleware.ts`) refreshes the session before protected routes render — a Server Component cannot write cookies, so without it the refresh token is never persisted and users get logged out at random. Authorization lives in a data-access layer (`src/lib/dal/auth.ts`) that reads the `profiles` row from Postgres: `requireUser()` / `requireAdmin()` run in server layouts and redirect. Role is never read from the browser.

**Tech Stack:** next 16.4.6 · react 19.3 · @supabase/ssr 0.12.7 · @supabase/supabase-js 2.119 · zod 4.6 · pg 8.23 (migrations) · vitest 5 · Supabase CLI (type generation)

**Spec:** `docs/superpowers/specs/2026-11-12-nuvakara-design.md` (§5.4 auth model, §6.1 profiles, §7 RLS, §8 security)

## Global Constraints

- **Next.js 16.4.6**: `cookies()` and `headers()` are **async** — always `await`. `middleware.ts` was renamed to **`proxy.ts`** (one file per project, at `src/proxy.ts`, runtime `nodejs`, cannot be configured to edge). `params`/`searchParams` are Promises. `next build` does NOT run ESLint.
- **Passwords**: never stored, never logged, never echoed. Supabase Auth hashes with bcrypt.
- **Role source of truth**: the `profiles` row in Postgres. A role sent by the browser is never trusted. `role` and `status` columns cannot be changed by the owner (RLS + trigger guard).
- **Admin bootstrap**: `ADMIN_EMAILS` env var (comma separated). Promotion happens **on the server** inside the login action, idempotently, and is written to `admin_activity_logs`.
- **Suspension**: enforced in `requireUser()` (server), never in `proxy.ts` (it cannot know the profile status without a DB read per request, and a redirect loop is the alternative). A suspended user is redirected to `/login?suspended=1`.
- **Session**: httpOnly cookie via `@supabase/ssr`; `signOut()` invalidates server-side.
- **Validation**: zod on the server for every action; client validation is a convenience, never the guard.
- **Mobile-first**: forms full-width, inputs ≥ 16px, error messages adjacent to the field, buttons ≥ 44px.
- **Animation**: GSAP 3.15 + `@gsap/react` (see the plan's Global Constraints in Phase 1). Auth pages use the same tokens; page transitions come from `src/app/template.tsx` automatically.
- **No fake features**: every button on the auth pages performs a real server action; every error state is real (Supabase error messages are surfaced, never swallowed).
- **TypeScript strict**; no `any` in the public API.

## Review Focus

Five conditions the plan's tests do not obviously cover — each one gets a test in the task that owns the code:

1. **User registers while "Confirm email" is ON** → `signUp` returns no session. The register action must return a "check your email" state, not an error, and must not redirect to a dashboard that would bounce the user to login. → Task 4
2. **Session expires mid-visit** → the refresh token must survive in the cookie, otherwise the user is silently logged out. → Task 2
3. **A user whose email is in `ADMIN_EMAILS` signs in** → promoted to admin on the server, idempotently (signing in twice must not create two audit rows). → Task 3
4. **A suspended user hits `/dashboard`** → redirected to `/login?suspended=1`, never rendered, and never bounced in a redirect loop. → Task 3
5. **Wrong password / unknown email** → the same generic message, so the form never reveals whether an email is registered. → Task 4

**Interfaces:**
- Produces:
  - `createClient(): Promise<SupabaseClient<Database>>` — server client bound to the request cookies (`getAll`/`setAll`).
  - `createAdminClient(): SupabaseClient<Database>` — service-role client, `import "server-only"`.
  - `updateSession(request: NextRequest): Promise<NextResponse>` — refreshes the session, writes cookies onto the response, and optimistically redirects unauthenticated `/dashboard` & `/admin` traffic to `/login`.
  - `src/proxy.ts` exports `proxy` + a narrow `config.matcher`.

- [ ] **Step 1: Write the failing test** — asserts `server.ts` uses `createServerClient` with `getAll`/`setAll`, `admin.ts` imports `server-only` and the service-role key, `proxy.ts` exists and its matcher does not include every route.

- [ ] **Step 2: Run it, watch it fail.**

- [ ] **Step 3: Implement `src/lib/supabase/server.ts`**

```ts
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";

export async function createClient() {
  const cookieStore = await cookies();
  return createServerClient<Database>(url, key, {
    cookies: {
      getAll: () => cookieStore.getAll(),
      setAll: (cookiesToSet) => {
        try {
          cookiesToSet.forEach(({ name, value, options }) => cookieStore.set(name, value, options));
        } catch {
          // Called from a Server Component: cookies are read-only there.
          // src/proxy.ts is responsible for persisting refreshed tokens.
        }
      },
    },
  });
}
```

- [ ] **Step 4: Implement `src/lib/supabase/admin.ts`** — service-role client, `import "server-only"`, returns `null` when the key is missing.

- [ ] **Step 5: Implement `src/lib/supabase/session.ts` + `src/proxy.ts`**
  - `updateSession` builds a server client whose `setAll` writes to `request.cookies` **and** `response.cookies`, calls `supabase.auth.getUser()`, then redirects `/dashboard/*` and `/admin/*` to `/login?next=…` when there is no user.
  - `proxy.ts` matcher: `["/dashboard/:path*", "/admin/:path*", "/profile"]` only — a narrow matcher keeps the per-request network call off every route (including prefetches).

- [ ] **Step 6: Verify, then commit.**

- Create: `src/lib/dal/auth.ts`
- Test: `tests/unit/dal-auth.test.ts`

**Interfaces:**
- Produces:
  - `getUser(): Promise<User | null>` — the authenticated user, or `null`.
  - `getProfile(): Promise<Profile | null>` — the caller's `profiles` row (RLS-scoped).
